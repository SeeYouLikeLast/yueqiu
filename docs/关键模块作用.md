# 7. RocketMQ 在这里的作用

RocketMQ 在这里的核心作用是：**异步削峰、解耦、提升秒杀接口响应速度**。

---

## 7.1 没有 RocketMQ 的流程

如果没有 RocketMQ，秒杀请求可能是这样：

```
用户点击秒杀  ↓后端查库存  ↓扣库存  ↓插入订单  ↓返回结果
```

问题是秒杀高并发时，数据库压力会很大：

```
大量用户同时请求  ↓大量线程同时打数据库  ↓数据库连接被打满  ↓库存行锁竞争严重  ↓接口变慢甚至崩掉
```

---

## 7.2 有 RocketMQ 的流程

使用 RocketMQ 后，流程变成：

```
用户点击秒杀  ↓后端先用 Redis 快速判断库存和一人一单  ↓Redis 预扣成功  ↓发送一条订单消息到 RocketMQ  ↓接口立即返回 orderId  ↓消费者慢慢从 RocketMQ 拉消息  ↓异步创建数据库订单
```

这样请求线程不用等待数据库订单真正创建完成。

---

## 7.3 RocketMQ 承担了什么职责？

### 第一，削峰填谷

秒杀请求可能瞬间有 1 万个。

但数据库可能只能稳定处理每秒 500 个订单。

RocketMQ 可以先把订单消息存起来：

```
1 万个请求  ↓进入 MQ 队列  ↓消费者按数据库能承受的速度慢慢处理
```

这就叫削峰。

---

### 第二，异步处理

用户提交秒杀时，不需要同步等待数据库插入订单完成。

接口只要完成：

```
Redis 预扣成功 + MQ 发送成功
```

就可以返回：

```
{  "orderId": 10001}
```

真正插入订单由 `SeckillOrderConsumer` 后台完成。

---

### 第三，解耦

`SeckillService` 只负责：

```
校验资格扣 Redis 库存发送消息
```

`SeckillOrderConsumer` 负责：

```
消费消息创建订单扣数据库库存
```

两边通过 RocketMQ 连接，不直接耦合。

---

### 第四，支持失败重试

正常情况下，如果消费者处理消息时抛出异常，RocketMQ 可以重新投递消息，让消费者稍后再试。

但是你的当前代码里需要注意：`BusinessException` 被 catch 住了，并没有继续抛出。

这意味着对于 `BusinessException`，RocketMQ 可能会认为这条消息已经消费成功，不会再重试。
