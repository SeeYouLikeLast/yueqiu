## RocketMQ
但如果是“抢购成功后异步创建订单”这种典型交易业务，通常 **RocketMQ 更贴合**；如果企业已经把 Kafka 作为统一事件平台，或者秒杀消息还要进入实时计算、风控、推荐和数据分析链路，也可以继续使用 Kafka。
RocketMQ 更偏向“业务消息”，官方直接提供事务消息、顺序消息、延时消息、消费重试和死信队列等能力；其官方介绍也明确提到它源自阿里高并发电商业务。

|秒杀需求|RocketMQ 对应能力|
|---|---|
|秒杀请求排队、削峰|普通消息|
|创建订单失败后重新处理|消费重试|
|多次失败后人工补偿|死信队列|
|订单超过 15 分钟未支付|延时消息|
|同一订单状态按顺序变化|顺序消息|
|本地事务与发消息保持最终一致|事务消息|
RocketMQ 消费失败后可以按照**重试策略**重新投递，超过最大次数后进入**死信队列**；**延时消息则适合订单超时**、任务定时触发等业务。

例如**订单超时关闭**---**下一步优化**：

```
订单创建成功
    ↓
发送“15 分钟后检查订单”延时消息
    ↓
15 分钟后消费
    ↓
订单是否已支付？
 ├─ 已支付：忽略
 └─ 未支付：关闭订单并释放库存
```

RocketMQ 的事务消息用于保证“消息发送”和“本地事务”的最终一致性，因此比较适合订单、支付、库存等业务状态变化。
Redis 负责：库存预扣、资格判断、重复购买校验
RocketMQ 负责：秒杀请求排队、削峰、异步下单、重试和死信
MySQL 负责：订单和最终库存的持久化
延时消息 负责：未支付订单超时关闭


Kafka 的核心定位是**分布式事件流平台**，强调大规模事件的持久化、高吞吐数据管道、流处理和数据集成。
例如秒杀产生的事件需要同时**给多个系统使用**：

```
秒杀订单事件
 ├─ 订单系统
 ├─ 实时风控
 ├─ 用户行为分析
 ├─ 推荐系统
 ├─ 实时大屏
 ├─ 数据仓库
 └─ 日志审计
```

这时 Kafka 很合适，因为同一份事件可以由不同消费者组独立订阅和处理，并且可以保留、回溯和重新消费事件。Kafka 的消费者按日志偏移量拉取数据，可以调整位置重新消费
如果企业已经把 Kafka 作为统一事件平台，或者秒杀消息还要进入实时计算、风控、推荐和数据分析链路，也可以继续使用 Kafka。
