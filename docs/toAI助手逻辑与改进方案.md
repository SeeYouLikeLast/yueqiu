# AI 助手逻辑与改进方案

## 当前定位

AI 助手不是单纯聊天，而是“业务推荐助手”：

- 找附近场所。
- 推荐可购买场馆团购。
- 查找可加入约球活动。
- 推荐装备或秒杀装备。
- 给出选择依据，并返回可点击业务卡片。

入口：

- 底部导航：`助手`。
- 所有页面右下角：`AI 助手` 悬浮按钮。

## 技术栈

| 层     | 技术                                                           |
| ----- | ------------------------------------------------------------ |
| 前端    | Vue 3 + Vite                                                 |
| 后端    | Spring Boot                                                  |
| AI 框架 | Spring AI Alibaba                                            |
| 模型    | DashScope `qwen-plus`                                        |
| 会话存储  | MySQL `agent_conversation`、`agent_message`                   |
| 限流    | Redis                                                        |
| 业务工具  | Place / VenueProduct / Activity / Equipment / UserPreference |

配置：

```powershell
$env:AI_DASHSCOPE_ENABLED="true"
$env:AI_DASHSCOPE_API_KEY="你的百炼或 DashScope API Key"
$env:AI_MODEL="qwen-plus"
.\start-dev.bat
```

## 请求流程

接口：

```text
POST /agent/chat
```

请求关键字段：

```json
{
  "conversationId": 123,
  "message": "今晚附近能打羽毛球吗",
  "sportCode": "badminton",
  "sportCodes": ["badminton", "table_tennis"],
  "city": "西安",
  "lng": 108.94,
  "lat": 34.34
}
```

后端主流程在 `AgentServiceImpl.chat`：

1. 检查 AI 开关。
2. 获取当前用户；未登录用户使用 `userId=0`。
3. 做 Redis 限流。
4. 创建或复用会话。
5. 保存用户问题。
6. `buildContext` 调用业务工具，组装候选卡片。
7. `callModelOrFallback` 调用 DashScope 解释候选卡片，或本地兜底回答。
8. 保存助手消息和卡片。
9. 返回答案、卡片、下一步快捷问题。

关键约束：

- 后端先查业务工具，再把整理后的 `cards` 交给模型。
- 模型不再临场自主调用业务工具，避免绕过后端筛选规则。
- 没有真实候选卡片时，不调用模型自由回答，直接提示“暂时没有找到合适结果”。
- 装备、场馆团购、秒杀等交易相关回答必须引用真实卡片里的商品名和价格。
- 装备、秒杀装备、明确时段的场馆团购采用强约束回答：后端直接用真实卡片生成解释，避免模型编造商品或把上午券解释成晚间可用。
- 如果模型回答没有命中候选卡片标题，后端会回退到本地可信回答，避免出现不存在的商品。

## 意图识别

当前使用轻量关键词识别：

| 意图 | 关键词 |
| --- | --- |
| 场所/团购 | 场所、场馆、球馆、附近、场地、哪里、私教、团购 |
| 约球活动 | 约球、活动、加入、搭子、局 |
| 装备 | 装备、球拍、球鞋、护具、球包、购买、买 |
| 秒杀 | 秒杀、特价、抢购、便宜 |

如果没有识别出明确意图，则认为是宽泛问题，会同时查场所、活动和装备。

## 运动类型选择

优先级：

1. 前端快捷问题多选的 `sportCodes`。
2. 前端当前选中的 `sportCode`。
3. 从用户自然语言中猜测球类。
4. 为空时查全部运动。

前端快捷问题点击后会弹出球类选择：

- 不限。
- 单选。
- 多选。

这样用户点击“今晚附近能打球吗”时，可以先选择羽毛球、乒乓球等，再查询。

## 工具调用

### 场所工具

`PlaceAgentTool.searchNearbyPlaces`

- 调用高德附近搜索。
- 依赖前端定位经纬度。
- 返回真实 POI。
- 卡片包含距离、区域、球类、封面、跳转动作。

### 场馆商品工具

`VenueProductAgentTool.searchVenueProducts`

- 根据 `sportCode + placeRank` 查询本地场馆商品。
- 支持预算过滤。
- 支持时间倾向排序：
  - `今晚/晚上/下班后/19:00/20:00` 优先晚间或单场 1 小时。
  - `上午/早场/08:00-12:00` 优先上午畅打套餐。
  - 没有完全匹配时，优先给可预约的单场项目，不把上午券解释成晚间可用。
- 返回可买团购卡片。

### 约球活动工具

`ActivityAgentTool.searchJoinableActivities`

- 查询同城、同运动、可加入活动。
- 排除当前用户自己。
- 卡片包含活动时间、人数、水平、费用。

### 装备工具

`EquipmentAgentTool.searchEquipment`

- 根据运动类型、关键词、预算查询装备。
- 装备数据有适合人群、优点、缺点。

### 用户偏好工具

`UserPreferenceAgentTool.getCurrentUserPreference`

- 获取登录用户城市、水平、偏好时间等。
- 用于个性化推荐解释。

## 模型输入与输出

后端不会把全部内部字段都交给模型。传给模型的是整理后的候选数据：

```text
type
title
subtitle
price
tags
distanceMeters
rating
reviewCount
available
stock
suitableLevel
sceneTags
pros
cons
recommendScore
recommendReasons
```

不希望模型暴露给用户的字段：

```text
placeRank
id
payload
meta
action
```

模型回答后会经过 `sanitizeAnswer`，去掉明显的内部字段。

## 前端展示

前端显示：

- 用户问题气泡。
- AI 思考中状态。
- AI 文本回答。
- 横向滑动业务卡片。
- 下一步可问的问题。
- 固定底部输入框。

卡片动作：

| 卡片类型 | 动作 |
| --- | --- |
| `place` | 跳转场所详情 |
| `venue_product` | 跳转场馆团购 |
| `activity` | 加入活动或跳转约球 |
| `equipment` | 跳转装备详情 |
| `seckill` | 跳转秒杀装备 |

所有写操作仍由前端二次确认或用户点击按钮触发，AI 不自动下单。

## 当前缺陷

### 1. 意图识别偏简单

当前主要靠关键词，复杂句子会误判。

例：

```text
我今天不想打，只想看看附近有没有周末能订的场地
```

可能只识别到“附近/场地”，但没有理解“周末”。

改进：

- 增加一个轻量 NLU 解析层，提取运动、时间、预算、距离、水平。
- 或让模型先输出结构化 JSON，再调用工具。

### 2. 推荐排序还不够体系化

当前是工具先查候选，再由模型解释。排序更多依赖查询顺序。

改进：

后端先做结构化推荐分：

场所推荐：

```text
距离 25%
可购买/可预约 20%
价格 20%
评分/评价数 15%
设施匹配 10%
用户偏好匹配 10%
```

装备推荐：

```text
预算匹配 25%
运动类型匹配 20%
水平匹配 20%
评分/销量 15%
库存 10%
活动价格 10%
```

约球推荐：

```text
时间匹配 30%
水平匹配 20%
距离 20%
剩余人数 15%
组织者可信度 10%
费用 5%
```

模型负责解释“为什么选 A，不选 B”。

### 3. 多轮记忆还比较弱

MySQL 已保存会话，但 Redis 短期上下文和历史摘要还不充分。

改进：

- 最近 10 条消息放 Redis。
- 长历史做摘要，保存在 MySQL。
- 让模型知道用户上一轮已经看过哪些场所，避免重复推荐。

### 4. 工具调用不是完整 Agent Graph

当前是后端固定调用工具，再交给模型回答，不是模型自主规划多步骤。

改进：

- 引入 Spring AI Alibaba 的 Agent/Graph 能力。
- 步骤变成：理解需求 -> 规划工具 -> 查询 -> 排序 -> 生成答案。

### 5. RAG 还未接入

当前只检索结构化数据，没有检索博客、评价、装备心得的语义内容。

改进：

- 对博客、评价、装备描述做向量化。
- 引入向量数据库。
- 支持“这个场馆环境怎么样”“这个球拍适合新手吗”这类主观问题。

### 6. 数据字段还可以更丰富

当前演示数据已经加入差异，但真实业务还需要：

- 场馆实时拥挤度。
- 退款规则结构化。
- 教练可约时间。
- 用户历史消费偏好。
- 用户常用位置。

## 下一步建议

短期优先级：

1. 做后端推荐评分，不完全依赖模型自由判断。
2. 增加时间解析，例如“今晚 7 点”“周末上午”。
3. 把博客和评价摘要纳入 AI 候选数据。
4. 给 AI 卡片增加“为什么推荐”字段。

中期优先级：

1. MySQL 保存完整会话，Redis 保存短期上下文。
2. Agent Graph 多步骤规划。
3. RAG 检索博客、评价、装备心得。
4. 写操作统一走“AI 推荐 -> 用户确认 -> 业务接口”的闭环。
