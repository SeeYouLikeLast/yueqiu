# 轻量演示数据方案

## 目标

本方案用于本地演示和答辩展示，不追求海量压测。核心目标是：

- 首页场所仍然通过高德 API 获取真实附近场所。
- 本地 MySQL 只保存平台业务数据，例如团购、装备、订单、博客、约球活动。
- 场馆商品、库存、教练、场馆号、评价按“搜索结果顺序槽位”绑定，减少演示数据准备成本。
- 图片统一走 MinIO 元数据，不再依赖外部图片热链。
- 数据量够展示即可，同时保留距离、价格、水平、设施、优缺点等差异，便于 AI 助手做推荐解释。

## 场所绑定规则

演示版不把团购、教练、场馆号、评价强绑定到真实 `amap_place_id`，而是使用：

```text
city + sport_code + place_rank
```

含义：

- `city`：城市，例如 `西安`。
- `sport_code`：球类，例如 `badminton`。
- `place_rank`：当前高德搜索结果中的第 N 个场所。

示例：

```text
西安 + badminton + rank 1
```

表示“西安羽毛球搜索结果中的第 1 个场所”挂载一组演示团购、库存、教练、场馆号和评价。

用户下单时仍然保存当前真实高德场所快照：

```text
amap_place_id
venue_name
longitude
latitude
```

这样即使高德排序变化，历史订单仍然能显示当时的真实场所名称。

## 差异化设计

### 场所

每个城市、每种球类有 2 类场所模板：

| 槽位 | 定位 | 优点 | 不足 |
| --- | --- | --- | --- |
| rank 1 | 通勤快打 | 近地铁、夜场灯光、预算友好 | 晚高峰拥挤、停车少 |
| rank 2 | 品质训练 | 空调、停车、淋浴、专业地胶 | 价格高、距离略远 |

### 场馆商品

每个球类、每个槽位有 3 类商品：

| 商品类型 | 场景 | 差异点 |
| --- | --- | --- |
| `TIME_PACKAGE` | 上午低峰畅打 | 价格低，适合新手练习 |
| `COURT_SLOT` | 晚间黄金单场 | 热门时段，余位更少 |
| `COACH_LESSON` | 私教体验课 | 基础纠错或进阶训练 |

普通商品中有一部分没有 `original_price`，或者不展示折扣，避免所有商品都像秒杀。

### 装备

每种球类 3 件装备：

- 入门款：价格低、容错高，但上限有限。
- 进阶款：支撑、控制或稳定性更好，价格中等。
- 专项/高端款：适合高强度或特定打法，但对水平和预算要求更高。

装备描述中显式写入：

```text
适合
特点
优点
不足
```

便于 AI 助手给出选择依据。

### 博客与评价

- 博客关联 `EQUIPMENT` 或 `VENUE_PRODUCT`，用于社区瀑布流和 AI 检索展示。
- 场馆评价严格使用同城市、同球类用户，避免足球场展示羽毛球评价、外地球友评价。

数据库中的图片地址统一使用：

```text
/objects/hm-badminton/{objectName}
```

## 执行方式

在项目根目录执行：

```powershell
.\scripts\seed-light-demo.ps1
```

只重新生成 SQL，不重新生成图片、不上传 MinIO：

```powershell
.\scripts\seed-light-demo.ps1 -SkipAssets -SkipUpload
```

脚本输出：

```text
backend/src/main/resources/db/data.sql
seed-assets/generated/
```

如果 `hm-badminton-minio` 容器正在运行，脚本会自动把 `seed-assets/generated/demo` 上传到 MinIO 的 `hm-badminton` bucket。

## 后续扩展

演示阶段使用 `place_rank` 可以显著减少数据准备成本。生产阶段建议逐步迁移到 `amap_place_id` 强绑定：

- 场馆商品
- 驻场教练
- 场馆号
- 场馆评价
- 场馆公告
- 场馆优惠券

迁移后需要增加一个“场所认领/绑定”后台流程，确保平台商品和真实高德 POI 的关系稳定。
