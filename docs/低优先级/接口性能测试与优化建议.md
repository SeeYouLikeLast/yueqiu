# 接口性能测试与优化建议

## 1. 测试方式

当前项目提供了轻量级接口性能测试脚本：

```powershell
.\scripts\test-api-performance.ps1
```

默认配置：

- 后端地址：`http://localhost:8088`
- 每个接口请求次数：`20`
- 预热次数：`2`
- 登录账号：`demo001@example.com`
- 登录密码：`123456`
- 默认不压测高德接口，避免第三方网络、限流和配额影响本地结果

如果需要把高德附近场所接口也纳入测试：

```powershell
.\scripts\test-api-performance.ps1 -IncludeAmap
```

最近一次测试结果保存位置：

```text
logs/api-performance-20260710-230834.json
```

## 3. 结果分析

整体情况：

- 当前轻量演示数据规模下，核心读接口平均耗时基本在 `15ms - 40ms`。
- 所有被测接口错误数为 `0`，说明登录、鉴权、订单查询、博客查询、AI 状态接口的基本链路可用。
- 部分接口最大耗时明显高于平均值，主要是本地 JVM、MySQL、Redis、PowerShell 串行请求和开发环境波动导致。

相对更需要关注的接口：

- `/api/sports`：首批请求出现过百毫秒波动。该接口数据很稳定，已经适合 Redis 缓存，后续可以继续观察缓存命中率。
- `/api/social/activities`：最大耗时较高。约球活动会结合城市、运动、分页和成员数据，后续数据变多后需要关注索引。
- `/api/auth/me`：理论上应该很轻。如果波动持续偏高，需要检查 Token 刷新、Redis TTL 刷新和用户信息查询是否可以合并或缓存。
- `/api/blogs/of/follow`：关注流本身包含 Redis 收件箱、博客详情、作者信息、点赞状态等逻辑，后续做并发压测时要重点观察。

## 4. 下一步优化

短期优化：

- 稳定字典类数据继续走 Redis：`sports`、`categories`、热门运动配置。
- 给高频列表增加短 TTL 缓存：热门装备、热门场馆商品、约球活动列表。
- 检查订单、购物车、活动查询索引：`user_id`、`status`、`sport_code`、`city`、`created_at`。
- 博客列表继续坚持批量查询作者和状态，避免每条动态单独查用户、关注、点赞。
- 高德附近场所接口使用经纬度粗粒度缓存，避免同一位置反复请求第三方接口。

中期优化：

- 使用 JMeter、k6 或 Gatling 做并发压测，重点压测登录、秒杀、购物车支付、关注流。
- 接入 Micrometer + Prometheus + Grafana，观察接口耗时、数据库连接池、Redis 命中率和 RocketMQ 消费延迟。
- 打开 MySQL 慢 SQL 日志，超过 `200ms` 的 SQL 统一排查执行计划。
- 对 AI 助手接口拆分模型耗时和业务工具耗时，分别记录埋点。

长期优化：

- 场馆推荐、装备推荐、约球推荐可以先由后端计算结构化推荐分，再交给大模型解释。
- 高并发秒杀链路继续保持 Redis Lua 预扣库存、Redisson 一人一单、RocketMQ 异步落库。
- 对热点详情页采用逻辑过期或主动预热，减少缓存击穿风险。

## 5. JMeter 秒杀并发验证（2026-08-03）

测试计划位于 `scripts/jmeter/`，原始 JTL 和 HTML Dashboard 位于本地 `reports/jmeter/`，这些生成文件不提交 Git。

| 场景 | 采样 | 结果 | 正确解释 |
| --- | ---: | --- | --- |
| 同一 Token 并发抢购 | 100 | 1 个 200、99 个 409 | 一人一单生效，409 是预期业务拒绝 |
| 50 用户普通并发 | 50 次登录 + 50 次秒杀 | 33 次抢购成功、17 次 400 | 库存耗尽后拒绝，不应计作服务崩溃 |
| 50 用户同步起跑 | 50 次登录 + 50 次秒杀 | 29 次抢购成功、21 次 400 | 不同测试轮次剩余库存不同 |

JMeter Dashboard 会把 400/409 统计为 `errorPct`，因此同一 Token 场景会显示 99% 错误率。这里的 HTTP 冲突是业务正确性结果，不能直接解释成系统失败率。真正的技术错误应单独检查 5xx、连接超时和后端异常日志。

本次同步起跑整份采样的吞吐约 `29.8 requests/s`，P95 约 `1.98s`；普通并发约 `18.9 requests/s`，P95 约 `3.67s`。采样包含登录、跨公网网络和 2GB ECS 资源限制，只能说明当前演示环境能正确处理这一档请求，不能代表秒杀接口的独立极限 TPS。

下一轮容量测试应：

1. 预先准备独立账号和足够库存，登录与秒杀分开统计。
2. 分别测试 50、100、200、500 并发，每档至少执行 3 次。
3. 同时记录 ECS CPU、内存、Swap、JVM、Hikari、Redis 和 MySQL 指标。
4. 测试后核对 Redis 库存、MySQL 订单数、用户唯一订单数和商品库存，证明不超卖且数据一致。
5. 使用隔离测试活动，避免压测污染演示订单。

## 6. 当前验收结论

- 读接口在轻量演示数据下基本可用。
- 秒杀的一人一单和库存拒绝行为符合预期。
- 现有数据不足以给出商业容量承诺，不能把 `29.8 requests/s` 写成系统最大并发量。
- 重大上线边界见 [最终版评审与验收清单](../最终版评审与验收清单.md)。
