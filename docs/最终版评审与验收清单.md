# 最终版评审与验收清单

更新时间：2026-08-03

## 1. 结论

当前版本可以作为毕业设计、课程项目、作品集和小规模演示系统交付。核心链路完整，前后端能够构建，ECS 已部署，登录、场所、团购、装备、购物车、普通订单、秒杀、社区、约球和 AI 助手均有实际代码闭环。

当前版本不能直接宣称为商业生产系统，主要差距不是页面功能，而是支付合规、密钥治理、高可用、备份恢复、监控告警和容量验证。

## 3. 上线前必须处理的 P0 问题

### 3.1 轮换已经出现过的密钥

仓库历史和开发配置曾出现高德 Key、开发数据库密码和 MinIO 默认凭据。`.gitignore` 只能阻止未来提交，不能清除 Git 历史或撤销已经泄露的凭据。

必须执行：

1. 在高德控制台重建 Web 服务 Key 和 JS Key，并限制可调用 API、Web 域名、配额和告警。
2. 轮换 ECS 的 MySQL、MinIO、DashScope、SMTP 和 Token/JWT 密钥。
3. 只在 `/etc/hm-badminton/app.env`、`deploy/production/.env` 保存真实值，权限设为 `600`。
4. 公共仓库发布前使用密钥扫描工具检查当前分支和历史提交。

详见 [生产安全与密钥管理](生产安全与密钥管理.md)。

### 3.2 明确支付只是模拟支付

当前 `/payments` 是“创建订单并立即置为已支付”的演示链路，没有第三方支付回调、签名验签、支付流水、重复回调幂等、退款、关单和对账。任何真实收费场景都必须先接入支付宝、微信支付或受监管支付服务。

### 3.3 建立可恢复的备份

生产数据不能只依赖 Docker Volume。至少要有 MySQL 每日备份、MinIO 对象备份、配置备份，并完成一次恢复演练。Redis 是可重建临时态，不是订单事实来源。

详见 [备份、恢复与监控](备份恢复与监控.md)。

### 3.4 保证生产 Profile 正确

开发默认配置会执行 `schema.sql` 和 `data.sql`。ECS 必须保持：

```text
SPRING_PROFILES_ACTIVE=prod,lite
```

或启用 MQ 时使用 `prod,mq-lite`。缺少 `prod` 有重建演示数据库的风险。更新部署时禁止再次运行 `initialize-demo-data.sh`，禁止执行 `docker compose down -v`。

## 4. 重要但不阻塞演示的 P1 问题

| 问题 | 当前影响 | 建议 |
| --- | --- | --- |
| 单 ECS 单实例 | 主机、磁盘或进程故障会整体不可用 | 数据库托管化、对象存储 OSS、至少双实例应用 |
| 缺少统一监控 | 慢在高德、MySQL、Redis 还是模型只能查日志 | Micrometer、Prometheus、Grafana、告警 |
| 手工 SQL 迁移 | 多环境升级容易漏执行或顺序错误 | 引入 Flyway/Liquibase，生产禁止 `schema.sql` 重建 |
| `App.vue` 体积过大 | 页面状态耦合，容易出现滚动和返回状态回归 | 拆 Router、页面组件、Pinia Store 和组合式函数 |
| 文件只校验扩展名和 MIME | 能阻挡普通误传，不能替代文件内容识别和病毒扫描 | 校验 magic bytes，私密附件独立 Bucket，增加扫描 |
| MinIO Bucket 公开读 | 适合公开头像/博客图，不适合隐私文件 | 拆成 public/private Bucket，私有文件鉴权下载 |
| AI 外部依赖 | DashScope 超时、限流或余额不足会降级 | 记录模型失败率、工具耗时、费用和降级率 |
| 压测规模有限 | 已证明并发约束，尚未确定容量上限 | 独立测试环境分档压测并监控资源 |

## 5. 已知业务边界

- 高德提供真实 POI；团购、库存、评价和订单是平台演示数据，不是高德或美团交易数据。
- 场馆商品按城市、球类和高德结果顺序挂载，适合轻量演示，不等于商家真实入驻关系。
- 秒杀轻量模式使用 Redis Lua、Redisson 和同步事务落库；启用 RocketMQ 后才展示完整异步削峰链路。
- AI 只推荐后端查询到的候选，写操作仍需要前端二次确认；模型回答不构成支付或场馆承诺。
- HTTPS 精确定位依赖用户授权、设备能力和浏览器实现；失败时回退到 IP 城市级定位，再回退西安。

## 6. 发布验收顺序

1. `git status` 确认没有 `.env`、日志、构建包和性能报告被提交。
2. 后端执行 `mvn test`。
3. 前端执行 `npm ci && npm run build`。
4. 备份 ECS 当前 JAR、前端目录、Nginx 配置和数据库。
5. 部署后端并检查 `systemctl is-active hm-badminton`。
6. 部署前端并检查首页引用了新的 Vite 哈希文件。
7. 执行 `nginx -t` 后平滑 reload。
8. 检查首页、`/api/sports`、登录、场所、社区、购物车、约球和 AI。
9. 检查 Nginx、Spring Boot、MySQL、Redis、MinIO 的错误日志和内存。
10. 出现异常时按备份版本回滚，不在生产库重新执行演示初始化脚本。

## 7. 最终交付标准

作为演示版，满足以下条件即可发布：自动化测试和构建通过；核心页面可操作；生产不自动清库；密钥未提交；HTTPS、证书续期、备份和回滚路径明确；模拟支付和演示数据在 README 中公开说明。

作为真实商业系统，还必须完成真实支付、隐私与合规、高可用、灾备演练、可观测性、安全测试和容量测试。
